# 📋 Spec

The detail a command is deliberately missing. **One task, generated by a planning command, consumed once by a build phase.** A spec is nothing more than that command's format template, filled in -- if the two drift, the template is the authority.

## Must contain

| Section | Holds |
|---|---|
| Title | The task type and its name |
| Metadata | Run identifier, and **the originating request verbatim** -- the spec must be readable without the tracker |
| Description | What is being done |
| Relevant files | Each with a reason it is listed; new files called out separately |
| Step-by-step tasks | Ordered, executable, **explicitly to be done in order** |
| Validation commands | **Literal commands**, each annotated with what passing proves |
| Notes | Anything that does not fit above |

**The last step always validates.**

## What planning owes, by task type

- **A defect:** reproduce it, or record why that is blocked and what supports the hypothesis, **before proposing a cause.**
- **A feature:** specify the user journey and the edge cases.
- **A chore or refactor:** specify the behaviour that must remain **unchanged**.

**A fresh builder must not need hidden conversation history.** If the spec only makes sense to someone who watched it being written, it is not finished.

**Planning does not mutate.** Scaffolding, installing dependencies and editing target code are not planning, whatever the phase is called.

## Varies by task type

A defect adds reproduction steps and root-cause analysis. A feature adds the user story, problem and solution statements, phased implementation, testing strategy and acceptance criteria. A chore adds nothing -- the minimum set is the whole spec.

Two ways to select those sections, and the choice matters: the **command** can decide, or the **spec's own metadata** can declare its type and complexity and the template branches. Metadata-driven is what lets an unclassified one-line request become a spec without a person triaging it first.

## Rules

- **Naming carries the type, the run identifier and a description.** All three, because specs are found by pattern as often as by path.
- **Machine-generated and short-lived.** One run, then dead. It is not documentation.
- **Validation commands are literal and runnable.** "Run the tests" is not a validation command.
