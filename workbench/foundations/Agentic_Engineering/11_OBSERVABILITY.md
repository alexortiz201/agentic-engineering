# 🔬 Observability and introspection

What changes when the thing being observed is a run rather than a service, and when the thing doing the observing is sometimes the run itself.

The classical definition still holds -- answer questions from what was already emitted, without modifying the thing to ask. Three things about it change here, and each inverts an instinct carried over from observing a service.

## A run is finite, so retain rather than sample

A service runs forever and you sample it. **A run is bounded, so the correct default is to keep all of it.** There is no long tail to manage; there is one execution, and its whole record is small compared with what it cost to produce.

The consequence is that a lost detail is unrecoverable in a way it is not for a service. A service will serve the same request again tomorrow. A run that discarded its compiled prompt cannot be asked what it was thinking, because the only copy is gone and re-running produces a different one.

## The input matters more than the output

For a service you mostly want to know what it *did*. For a run you mostly want to know what it was *given*, because that is what makes the result explicable and reproducible.

**Record the effective configuration, not the configuration as authored.** The compiled prompt rather than the template, the model that actually served the call, the tools that were genuinely available, the resolved working directory, the context that was actually loaded. A template plus a note saying which variables *should* have been substituted is not a record of what ran.

This is also the only way to tell two categories of failure apart. A run that produced a bad result from a good prompt is a different problem from one that produced a reasonable result from a prompt that was assembled wrong -- and without the compiled input, both look like the model being unreliable.

## The actor's account of itself is a claim

This is the distinction with no equivalent in service observability, and it is the one that matters most.

When deterministic code logs *"wrote the file"*, the log is a side effect of having written it. When an agent reports *"wrote the file"*, the report is **the agent's account of its own behavior** -- generated by the same process that may have failed to do it. It enters at the bottom of the evidence hierarchy and stays there, however fluent and well-formatted it is.

So an agentic observability record carries **two things per consequential step**: what the actor said it did, and what was independently observed. The file exists or it does not. The exit code was zero or it was not. The diff has content or it is empty. Where those disagree, the independent observation wins, and the disagreement is itself the most valuable thing the record contains.

**A record made only of agent self-reports is a transcript, not evidence.**

## Three surfaces that get conflated

The most common design mistake here is building one thing and expecting it to serve three purposes.

| | Consumer | Optimized for | Verbosity |
|---|---|---|---|
| **Channel** | the next phase | being consumed | verbose is fine -- it is transport |
| **Record** | a person reconstructing the run | reconstruction and audit | selected, not dumped |
| **History** | measurement across runs | aggregation | narrow, one entry per run |

**The channel is not the record.** What one phase hands the next is shaped for its consumer, and that consumer is frequently another agent, which tolerates and sometimes benefits from detail a person would drown in. Retaining the channel verbatim as the record produces a firehose nobody reads; summarizing the channel *into* the record loses the thing you will want. The answer is that they are different artifacts written at the same moment, not one artifact serving two readers.

**The record is not the history.** A record explains one run. A [history](primitives/run_history.md) is what makes a hundred runs comparable, and it stays narrow precisely so it can be queried rather than read.

## Introspection

Introspection is the system examining **its own** state and behaviour, as distinct from someone outside watching it. In agentic work it is not a luxury, because the actor best placed to notice that a run is going wrong is usually the one inside it.

What a run should be able to ask about itself: what it was actually given, what it has already done, what it has already tried and how that turned out, what remains in its budget, what state it is holding, and what the record says about previous runs of the same workflow. Each of those is an input to a decision the run is about to make -- whether to retry, whether to descend, whether to stop.

**And the limit, which is absolute.** Introspection produces claims subject to the same rule as every other self-report: an agent examining its own behaviour is still the actor reporting on itself. Self-examination is not self-verification. A run can and should read its own record to decide what to do next; it cannot use that reading to certify that what it did was correct, because the reading and the doing share an author.

The practical division: **introspection informs the run's decisions, and independent observation decides its gates.** A run that inspects its own output and concludes it passed has performed a self-assessment, which the gate rules already exclude by name.

## Observable is not interruptible

Everything above concerns what a run emits and what can be reconstructed from it afterwards. A second property is routinely assumed to arrive with it and does not: whether someone watching a run go wrong can act on that observation **while it is still running**.

A run that can only be read offers two moves once it is visibly off course -- let it finish, or end it -- and both discard the run. A run that can be attached to offers a third: correct it at the point the defect appeared, for the cost of the correction rather than the cost of the whole execution. **Watching a step without being able to reach into it is spectating**, and it delivers the observation at the moment it is least actionable. The supervised end of the autonomy ladder assumes the third move is available; nothing else in a run's design provides it.

The property has a price, which is why it is a decision rather than a default. An attachable run is one more thing that can be perturbed, so **an intervention is a change to the run and belongs in its record like any other** -- who, at which step, what was changed, and what the run was about to do instead. An unrecorded intervention is the most expensive kind of missing record: the run afterwards is no longer the run its configuration describes, and nothing downstream can tell it apart from a run that needed no help. That is also how a workflow acquires a reputation for working which belongs to the person who kept rescuing it.

## Scope a signal to the run, or it is measuring history

A log that is appended to across runs and never rotated holds every run the machine has ever performed. Counting matches over the whole file therefore answers a question nobody asked -- *has anything ever gone wrong here* -- while presenting as an answer to the one that was asked, which is whether anything went wrong **this time**.

The failure is not that the number is imprecise. It is that the number is **confident, specific and about the wrong interval**, which is the combination no reader is equipped to doubt. A count of errors scanned over an unrotated log once produced a firm reading of one hundred and ninety-one errors against a system that was in fact perfectly healthy, and sent an investigation after a defect that had been fixed days earlier. Nothing about the figure looked wrong.

Two remedies, and they are not equivalent:

- **Scan forward from a marker that identifies the start of this run**, and count only after it. This works on a shared resource nobody may rotate, which is the common case.
- **Rotate before starting**, so the artifact begins empty. Cleaner where the run owns the resource, and unavailable where it does not.

**When neither is possible, report that the signal could not be scoped -- and report no number at all.** This is the general rule about empty results arriving at a specific instrument: an unscoped count and a scoped one are indistinguishable once both are integers, so emitting the unscoped one launders "I could not look at the right interval" into a measurement. A stated inability to measure is a usable input to the next decision. A number about the wrong interval is worse than silence, because silence does not get acted on.

The same question applies to every accumulating signal, not only to logs -- a metric series, a queue depth, an error aggregator, a coverage report over a directory that holds more than the change. **Ask what interval a signal covers before reading it as a result**, and where the answer is "everything that has ever happened", it is not observing this run.

## What must be capturable

The minimum for a run to be explicable afterwards by someone who was not watching:

- Which model served each call, and the effective configuration around it.
- The compiled prompt, as sent.
- The tools actually available, and the workspace actually resolved.
- What each phase produced, and what each gate decided while observing what.
- What it cost and how long it took.
- Every point where a human intervened. Each one is an **entry in the run's action log**, carrying who, the step, what was changed, and what the run was about to do instead; the history's intervention count is derived from those entries rather than tracked beside them.

**If a defect can be present without any of these changing, none of them is observing it.** That question is worth asking of each signal before adding it, and it is the same counterfactual a check has to pass.
